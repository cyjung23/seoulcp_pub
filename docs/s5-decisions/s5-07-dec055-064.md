## DEC-055 — 백업 방식을 Artifact → `db-backup/` 직접 커밋으로 전환
결정일: 2026-07-04. 결정자: 원장님. 상태: 확정.

배경: 기존 GitHub Actions Artifact 방식은 90일 후 자동 삭제되고 raw URL 접근이 불가하여, 백업 내용 확인 시 매번 Artifact 다운로드가 필요해 효율이 낮았음.

결정 내용: `pg_dump` 결과물(`data.sql`, `schema.sql`)을 `seoulcp_pub/db-backup/` 디렉토리에 직접 커밋하는 방식으로 전환. 워크플로가 매일 KST 09:00 자동 push. 저장 위치는 `seoulcp_pub`에만 두고 `seoulcp`(Private 소스 저장소)에는 별도 백업을 두지 않음.

근거:
- 표준문서와 DB 덤프를 동일 저장소에 두어 "SCP 프로젝트 표준문서 저장소" 개념의 일관성 유지.
- Git 히스토리로 백업 변경 이력 추적 가능.
- raw URL로 AI 및 외부 도구가 즉시 접근 가능.
- Artifact 90일 제한에서 벗어나 영구 보존.

최근 조치:
- 워크플로 #84 race condition 해결.
- 임시 테이블 `_backup_data002_descriptions` 정리 → 백업 48줄 감소.
- Supabase Egress 사용량 39% (정상 범위).

관련 문서: `docs/s3-completed/s3-03-backup.md`

## DEC-056 — seoulclinicpick.com 메인 전환 (브랜치 분리 접근)
결정일: 2026-10-14. 결정자: 원장님. 상태: 확정 (Phase 1 착수).

배경: seoulcp.com은 축약어라 외국인 환자 대상 브랜드 전달력이 약함. seoulclinicpick.com은 URL만으로 "서울의 클리닉을 선별해주는 서비스"임이 직관적으로 전달됨. 현재 트래픽이 하루 20~30명(100% 네이버 유입, 롱테일 중심)이고 구글/백링크 자산이 미미하여 전환 리스크가 최소화된 적기임. 하지만 현재 100% 네이버 유입이므로 신규 도메인이 네이버에 독자 색인될 때까지 기존 도메인 리디렉션은 금지됨.

결정 내용:
- 최종 목표: seoulclinicpick.com으로 메인 브랜드 일원화. seoulcp.com은 리디렉션 전용으로 영구 보유.
- 아키텍처: **브랜치 분리 + Vercel 프로젝트 분리** 방식 채택 (옵션 2).
  - 저장소는 단일(cyjung23/seoulcp) 유지, 브랜치만 분리.
  - `main` 브랜치 → Vercel 프로젝트 A (seoulcp.com, freeze 상태 유지).
  - `scp-new` 브랜치 → Vercel 프로젝트 B (seoulclinicpick.com, 활성 개발).
  - 코드 머지는 단방향(main → scp-new)만 허용. 반대 방향은 Phase 4 통합 전까지 금지.
  - Supabase DB는 단일 인스턴스 공유 (두 사이트가 같은 콘텐츠 노출이 목표에 부합).
  - 코드 리팩토링은 전략 A(환경변수 단일 치환, `NEXT_PUBLIC_SITE_URL`) 채택. 브랜치 분리 덕분에 요청 호스트 기반 동적 canonical 로직 불필요.
- 전환 Phase:
  - Phase 1 (1~2주): scp-new 브랜치 생성, Vercel 프로젝트 B 생성, 환경변수 리팩토링, 서치어드바이저 등록.
  - Phase 2 (2~3개월): 네이버 색인 모니터링, seoulcp.com freeze 유지.
  - Phase 3 (3~4주): 점진적 301 리디렉션 (디렉토리 단위, 트래픽 적은 경로부터).
  - Phase 4 (전환 완료 후): scp-new를 main에 머지, 저장소를 단일 체계로 복귀.

근거:
- 격리 요구: seoulclinicpick.com 작업이 seoulcp.com에 영향을 주지 않아야 함. 브랜치+Vercel 프로젝트 분리로 코드·배포·환경변수·로그 완전 격리.
- 운영 복잡도: 저장소 자체 분리(옵션 3)는 운영 부담이 과도. 브랜치 분리는 Phase 4에서 머지만으로 단일 체계 복귀 가능.
- 리팩토링 단순화: 브랜치별 환경변수 분리로 canonical 동적 생성 로직 불필요 → 전략 A 적용.
- SEO 보호: 현재 100% 네이버 유입이므로 신규 도메인 색인 완료 후에만 리디렉션 전환. 중간 단계에서 두 도메인이 독립 서빙되어도 self-canonical로 복제본 판정 회피.

리스크 및 대응:
- 긴급 수정 전파 누락 → 매주 월요일 main → scp-new 머지 루틴 고정.
- Vercel 환경변수 설정 오류 → 프로젝트 생성 직후 체크리스트 검증.
- 신규 도메인 복제본 판정 → 환경변수 분리로 canonical 완전 격리.
- Phase 3 트래픽 급락 → canonical 분리/리디렉션 범위 축소로 단계적 롤백.
